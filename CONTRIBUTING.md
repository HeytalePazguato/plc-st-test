# Contributing to {{PROJECT_NAME}}

Thanks for your interest! Contributions of any size are welcome — bug
reports, fixes, new features, doc improvements.

## Branch flow

```
develop  →  release/<version>  →  main
```

- All feature work, bug fixes, and refactors target `develop`.
- `main` is reserved for stable releases — never PR directly to it.
- Release stabilization happens on `release/<version>` branches cut from
  `develop`.

See the [README's "Branching & releases"](README.md) section (or
[`BLUEPRINT.md`](BLUEPRINT.md)) for the full versioning, tagging, and CI flow.

## Pull requests

- One logical change per PR; keep diffs reviewable.
- Run lint + build + test locally before opening the PR.
- Add a changeset (`pnpm changeset`) and update the root `CHANGELOG.md` under `[Unreleased]` — see [Versioning and changelogs](#versioning-and-changelogs).
- Never bump package versions by hand in feature PRs — that happens on the release branch via `pnpm version-packages`.
- The `ci` workflow must pass before a PR can merge.

## Versioning and changelogs

This repository is a pnpm monorepo whose packages are versioned independently with [Changesets](https://github.com/changesets/changesets).

### 1. Every PR adds a changeset

Run `pnpm changeset`, pick the affected packages and bump types (patch / minor / major), and write a short user-facing summary. Commit the generated `.changeset/*.md` file with the PR. Use `pnpm changeset status --since=develop` to check what a branch will release. PRs that touch no published package (docs, CI, tooling) don't need one.

### 2. Two changelogs

Per-package `CHANGELOG.md` files are generated by Changesets when versions are bumped — never edit them by hand. The root `CHANGELOG.md` is the product-level [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) log; keep its `[Unreleased]` section current in the same PR as the change.

### 3. Release flow

1. Cut `release/x.y.z` from `develop`.
2. On that branch run `pnpm version-packages` (`changeset version`), which bumps package versions, updates internal dependency ranges, writes the per-package changelogs and consumes the changesets; move the root `[Unreleased]` entries under the new version heading.
3. Open a PR from `release/x.y.z` to `main`. Once merged, `release.yml` publishes the packages (`pnpm release`).

Emergency patches use the `hotfix/<version>` exception: branch from `main`, run `pnpm version-packages` there, PR straight to `main`, then merge `main` back into `develop`.

### 4. Deviation from project-blueprint

The project blueprint prescribes a single repo-root `VERSION` file as the source of truth. That does not fit a monorepo with independently versioned, separately published packages, so `VERSION` was removed: each package's own `package.json` `version` is authoritative, managed by Changesets. `@plc-st/core` exposes its version at runtime as `VERSION`, read from its `package.json`.

### 5. Package boundary rules

Dependency direction is enforced by ESLint `no-restricted-imports` per package glob and by `test/architecture.test.ts` (which checks every `packages/**/package.json` and all source imports):

- `@plc-st/project-model` imports no other workspace package.
- `@plc-st/plugin-api` may import only `@plc-st/project-model`.
- `@plc-st/ingestor-*` never import `@plc-st/core`, the CLI, or any dialect.
- `@plc-st/dialect-*` never import `@plc-st/core` or any ingestor.

## Commit messages

Conventional-commits style is appreciated:

```
feat: add <thing>
fix: handle <edge case>
docs: clarify <section>
chore(deps): bump <dep> from X to Y
ci: <workflow change>
```

The release-branch workflow looks for `[beta]` / `[rc]` keywords in commit
messages to choose pre-release stages — keep those out of normal commits.
